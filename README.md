# UrbanNexus — Residential Operations Platform

UrbanNexus is a full-stack residential complex management system built with Spring Boot 4.1 and React 19. It covers the
complete operational lifecycle of a residential community: resident and technician management, amenity and technician
booking, payment tracking with 18% GST, and an administrative audit trail.

---

## Architecture

### Backend: Spring Boot 4.1 + Java 17

The backend is a RESTful JSON API with JWT-based stateless authentication, on Spring Boot 4.1 (Spring Framework 7,
Spring Security 7, Hibernate 7, Tomcat 11, Jackson 3). `pom.xml` overrides Logback to 1.6.x because Spring Boot 4.1 still
manages a 1.5.x version affected by CVE-2026-19880; drop the override once Spring Boot ships Logback 1.6.3 or later.
Key layers:

- **Controller** — validates role-based access, maps HTTP requests to service calls
- **Service** — contains all business logic (`@Transactional` boundary guards multi-step operations)
- **Repository** — Spring Data JPA interfaces; native queries are written in PostgreSQL-compatible SQL
- **Security** — `JwtAuthenticationFilter` extracts claims from every request; `UserPrincipal` carries `role`,
  `residentId`, `techId`
- **Model** — JPA entities with a `@PrePersist` lifecycle hook on `Payment` that applies 18% GST before insert
- **Utilities** — Lombok (`@Data`, `@RequiredArgsConstructor`) eliminates boilerplate across all layers

### Frontend: React 19 + Vite + TypeScript

- Material UI (MUI) v9 for the component library; Font Awesome for supplemental icons
- Framer Motion for page transitions and component animations
- Axios with a JWT interceptor for authenticated requests; `jwt-decode` for client-side token parsing
- React Router DOM v7 for role-based view routing (Admin dashboard, Resident portal, Technician portal)

### Database Strategy

Production runs on **Supabase PostgreSQL**. Local development runs on an **embedded H2** database started in
`MODE=PostgreSQL`, so a single set of DDL, seed, and native-query SQL executes identically in both environments — with
no external database to install for local work.

| Profile | Database                                             | Init mode         | Purpose                             |
| ------- | ---------------------------------------------------- | ----------------- | ----------------------------------- |
| (none)  | Embedded H2, file-based, `MODE=PostgreSQL`           | `always`          | Local development — zero setup      |
| `prod`  | Supabase PostgreSQL via the transaction pooler (SSL) | `never` (default) | Deployed container (Docker sets it) |

**One dialect, two engines.** `schema.sql` and `data.sql` are written in portable, PostgreSQL-flavoured SQL that H2's
PostgreSQL compatibility mode understands verbatim:

- Auto-generated keys use `BIGINT GENERATED BY DEFAULT AS IDENTITY` (SQL-standard identity), mapping cleanly to
  Hibernate's `GenerationType.IDENTITY`.
- `technician.available` is a native `BOOLEAN`; seed data uses `TRUE`/`FALSE`.
- Because the `resident` seed rows carry explicit IDs (1–26), `data.sql` advances the identity counter with
  `ALTER TABLE resident ALTER COLUMN resident_id RESTART WITH 27` — syntax both engines accept — so the next
  app-generated insert cannot collide with a seeded ID.
- The overdue-payment query uses `NOW() - INTERVAL '30' DAY` (SQL-standard interval), which both engines parse.

**Local (H2)** re-runs `schema.sql` (drop + recreate) and `data.sql` on every start, giving a disposable, deterministic
dataset. The H2 console is available at `http://localhost:8080/h2-console` (JDBC URL `jdbc:h2:file:./data/urbannexus`).

**Production (Supabase)** defaults `spring.sql.init.mode` to `never` (via `DB_INIT_MODE`), so **restarts never drop or
reseed** — data persists. `ddl-auto: update` still reconciles the schema (adds missing tables/columns, never drops). To
seed a brand-new database once, deploy a single time with `DB_INIT_MODE=always`, then remove it. The full connection
string is supplied by the `DB_URL` environment variable — see [Environment Variables](#environment-variables) for how to
build it from Supabase's IPv4 transaction pooler.

## Business Logic

### Sign-up Utility — Admin-Provisioned Accounts

UrbanNexus has no public self-registration. All accounts are provisioned by the `SuperAdmin`. The lifecycle is:

1. **Admin creates resident or technician** via the admin dashboard (or `POST /api/residents` /
   `POST /api/technicians`).
2. **Backend auto-generates credentials** — username is derived as `<lowercase_name><id>` (e.g., `jane_smith42`;
   accents are stripped, other punctuation becomes `_`, and a name ending in a digit gets a separator, as in `ann1_2`).
   Residents and technicians share one username space, so a name+id that is already taken gets a `_2`, `_3`, … suffix,
   and usernames are capped at 50 characters. A random 12-character **temporary password** (unique per account, from
   `SecureRandom`) is bcrypt-hashed and stored in the `admin` table alongside a role and a FK link to the resident or
   technician record.
3. **Credentials dialog** — the API response returns `{ username, password }` in plaintext (only on creation or reset).
   The admin dashboard shows this in a one-time modal with copy buttons. The admin must share the credentials with the
   new user; they will not be surfaced again.
4. **User logs in** with the provided credentials. The Login page explicitly states that accounts can only be obtained
   from the administrator. After 5 consecutive failed attempts a username is locked out of login for 15 minutes (`429`).
5. **User must replace the temporary password** before doing anything else. While `must_change_password` is set, every
   endpoint except `GET /api/profile/me` and `PUT /api/profile/password` answers `403` with
   `"code": "PASSWORD_CHANGE_REQUIRED"`, and the UI shows only the change-password screen. The endpoint verifies the
   current password (bcrypt match), rejects reusing it, and requires at least 6 characters.
6. **Lost passwords** — the admin uses the key icon in the Resident Directory / Technical Crew tab
   (`POST /api/residents/{id}/reset-password`, `POST /api/technicians/{id}/reset-password`) to issue a new temporary
   password, which signs the user out everywhere and puts them back at step 5.

This design keeps account provisioning entirely inside a trust boundary (only authenticated admins can create accounts)
while giving users ownership of their credentials after first login.

### Roles

| Role         | Capabilities                                                                            |
| ------------ | --------------------------------------------------------------------------------------- |
| `SuperAdmin` | Full CRUD on residents/technicians/amenities; confirm payments; reset user passwords    |
| `Resident`   | View own dues and report offline payments; book technicians and amenities; view history |
| `Technician` | View own task assignments; mark own tasks Completed; toggle availability                |

### Booking Flow

1. Resident requests a technician booking (`skill`, `slot` 1–3, `assign_date` as `YYYY-MM-DD`, today or later in the
   community's time zone, `APP_TIMEZONE`)
2. System locks every technician with that skill (`SELECT … FOR UPDATE`) and picks the first available one with no
   assignment in that slot on that date. Concurrent requests for the same skill wait on the lock, so two residents can
   never be given the same technician for one slot; a unique `(tech_id, assign_date, slot)` constraint enforces the
   same rule in the database. If nobody is free the request fails with `409`.
3. A `Payment` record is created with base price — `@PrePersist` automatically applies 18% GST
4. An assignment record is created in `technician_management` linking resident, technician, and payment
5. The response returns `assignment_id`, `technician_name`, `trans_no`, and `total_with_gst` (GST-inclusive cost)

Amenity booking follows the same pattern: capacity validation → payment with GST → booking record. Capacity is per
date and slot and counts every confirmed booking already made for it: the amenity row is locked while the requested
headcount (at least 1) is checked against the places left, so simultaneous bookings cannot oversell it. A request that
does not fit returns `409` with the number of places left. An amenity with no capacity set has no headcount limit. The
response returns `booking_id`, `amenity_name`, `trans_no`, and `total_with_gst`.

### Payment Lifecycle

There is no payment gateway, so the app never treats money as received on the resident's word alone:

```txt
Pending ──30 days──▶ Overdue          (nightly at 02:00, or admin's "Run Overdue Scan")
Pending / Overdue ──▶ Under Review    (resident: POST /api/payments/{trans_no}/submit  {"reference": "UPI-…"})
Under Review ──────▶ Paid             (admin: POST /api/payments/{trans_no}/confirm)
Under Review ──────▶ Pending/Overdue  (admin: POST /api/payments/{trans_no}/reject — back to whichever applies by age)
Pending / Overdue ──▶ Paid            (admin records an offline payment directly with /confirm)
Pending / Overdue / Under Review ──▶ Written Off   (admin deletes the resident and agrees to write the debt off)
```

A resident can only submit their own unpaid invoices, and must give a payment reference (UPI ID, cheque number, …) that
the admin sees in the Financial Ledger. Invoices under review still count as outstanding on the admin dashboard. Every
submit, confirm and reject is written to the audit log.

**Deleting a resident who owes money.** `DELETE /api/residents/{id}` is refused with `409` and
`{"code": "UNPAID_INVOICES", "unpaid_count", "unpaid_total"}` while the resident has Pending, Overdue or Under Review
invoices. The admin UI then offers to write the debt off; confirming repeats the call with `?write_off_unpaid=true`,
which marks those invoices `Written Off` (kept in the ledger, no longer counted as owed) and deletes the resident. All
of
the resident's invoices keep their name (`payment.billed_to`), so the ledger shows them as a former resident instead of
"UrbanNexus System".

**Invoice dates.** `payment.payment_date` is when the invoice was **issued** (the booking was made) — the 30-day overdue
rule counts from it. `payment.paid_at` records when the admin confirmed the payment, and the ledger shows it as "Paid
on".

**Who an invoice belongs to.** Each invoice records its resident in `payment.resident_id` (set when the booking is
made; older invoices are linked at startup from their booking). It is deliberately not a foreign key, so an invoice
keeps its owner when the booking behind it disappears. A technician with open (Assigned) jobs, or an amenity with
upcoming bookings, cannot be deleted (`409`); once their work is in the past they can be, and residents still see and
can settle the related invoices. Technician skills are restricted to the services on the price list and can only be
changed by the admin (`PUT /api/technicians/{id}`), and renaming an amenity carries its price over to the new name.

### GST via @PrePersist

The `Payment` entity applies an 18% GST multiplier before every insert:

```java

@PrePersist
public void calculateGST() {
    if (this.cost != null) {
        this.cost = this.cost.multiply(new BigDecimal("1.18")).setScale(2, RoundingMode.HALF_UP);
    }
    if (this.paymentDate == null) this.paymentDate = LocalDateTime.now();
}
```

Seed data in `data.sql` stores costs at face value (pre-GST); the hook fires on every `save()`.

### Audit Trail

All critical mutations (resident/technician add/delete, task status changes, availability toggles, payment reviews,
password resets, write-offs) are written to `audit_log` via `AuditService` inside the same transaction as the mutation
itself: if the change rolls back, so does its log entry, and logging uses no extra database connection. Each entry
records who made the change (`changed_by`: the signed-in username, or `system` for scheduled jobs). Auditing lives
entirely in the application layer, so it is database-agnostic and needs no engine-specific triggers.

## Running Locally

### Prerequisites

- JDK 17
- Maven 3.8+ (or `mvnw` if added to the project)
- Node.js 18+

No database install is needed for local development — the default profile uses an embedded H2 database.

### Environment Variables

Secrets are never hard-coded; they are read from the environment. Non-secret connection parameters have sensible
defaults, but the two secrets below have **no default** and must be set.

| Variable               | Required in  | Default             | Notes                                                                                                                                                                                                              |
| ---------------------- | ------------ | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `JWT_SECRET`           | local + prod | _(none — required)_ | **Base64** string, ≥ 32 bytes decoded (the app Base64-decodes it; 48 bytes → HS384). Generate **once** with `openssl rand -base64 48`, then reuse the same value — a changing secret invalidates all issued tokens |
| `DB_URL`               | prod         | _(none — required)_ | The complete JDBC URL, credentials and options included (see below). Not used locally — the default profile is H2                                                                                                  |
| `DB_INIT_MODE`         | prod         | `never`             | Leave unset in normal operation. Set to `always` **once** to seed a brand-new database, then remove                                                                                                                |
| `APP_TIMEZONE`         | local + prod | `Asia/Kolkata`      | Time zone that decides "today" for booking dates (the server itself usually runs in UTC)                                                                                                                           |
| `CORS_ALLOWED_ORIGINS` | prod         | _(none — required)_ | Comma-separated origin(s) of the deployed frontend, e.g. `https://urbannexus.onrender.com`. Unset → browsers are refused all API calls. Locally defaults to `http://localhost:*`                                   |

Local development (H2) only needs `JWT_SECRET`.

**Building `DB_URL` for Supabase.** Use the **Transaction pooler** connection string (Supabase dashboard → Connect),
convert it to JDBC form, and append two required options:

```txt
jdbc:postgresql://aws-0-<region>.pooler.supabase.com:6543/postgres?user=postgres.<project-ref>&password=<URL-ENCODED-PASSWORD>&sslmode=require&prepareThreshold=0
```

- The pooler host (`*.pooler.supabase.com`) is reachable over **IPv4**; the direct `db.<ref>.supabase.co` host is
  **IPv6-only** and fails on IPv4-only platforms such as Render.
- `prepareThreshold=0` is **required** — a transaction-mode pooler cannot share server-side prepared statements.
- **Percent-encode special characters** in the password (`#` → `%23`, `$` → `%24`, `!` → `%21`, etc.).

### Backend (local — embedded H2)

```bash
cd backend
# Generate the secret ONCE (e.g. `openssl rand -base64 48`), then reuse the same
# value on every run — a changing secret invalidates already-issued tokens.
export JWT_SECRET="paste-the-base64-value-here"
mvn spring-boot:run
```

Run the tests with `mvn test`. They use in-memory H2 databases; `PostgresCompatibilityIntegrationTest` also runs the
real `schema.sql`, `data.sql` and native queries against PostgreSQL 16 in a Docker container (Testcontainers) and is
skipped automatically when Docker isn't running.

On every start, `schema.sql` recreates all tables and `data.sql` seeds 26 residents, 16 technicians, 5 amenities, and
pricing. Inspect the data at `http://localhost:8080/h2-console` (JDBC URL `jdbc:h2:file:./data/urbannexus`, user `sa`,
empty password).

### Backend (Supabase — production profile)

```bash
cd backend
export JWT_SECRET="<your base64 secret>"
export DB_URL="jdbc:postgresql://aws-0-<region>.pooler.supabase.com:6543/postgres?user=postgres.<project-ref>&password=<URL-ENCODED-PASSWORD>&sslmode=require&prepareThreshold=0"
mvn spring-boot:run -Dspring-boot.run.profiles=prod
```

The `prod` profile connects to Supabase over SSL. Restarts do **not** drop or reseed data (`DB_INIT_MODE` defaults to
`never`). For the first-ever run against an empty database, add `export DB_INIT_MODE=always` to create the schema and
seed it, then unset it. The `Dockerfile` activates this profile automatically (`-Dspring.profiles.active=prod`); supply
`JWT_SECRET`, `DB_URL` and `CORS_ALLOWED_ORIGINS` (the frontend's URL) to the container's environment. In this profile
the H2 console is disabled and SQL statements are not logged.

## Key Design Decisions

**Admin-provisioned accounts, no self-registration** — There is no public sign-up endpoint. `POST /api/residents` and
`POST /api/technicians` are `SuperAdmin`-only and atomically create both the domain record and a linked login entry in
the `admin` table. The plaintext temporary password is returned once in the API response (and surfaced in the admin UI
as a one-time credentials dialog), after which only the bcrypt hash remains in the database. Each temporary password is
random and flagged `must_change_password`, so the account is unusable until its owner sets a password only they know.

**Booking logic in the service layer, not the database** — All booking, pricing, and payment logic lives in
`BookingService.java` inside a `@Transactional` boundary rather than in stored procedures. This keeps the behaviour
database-agnostic, unit-testable, and gives proper exception handling — and it means the migration to PostgreSQL touched
only DDL, config, and a couple of native queries, never the domain rules.

**`@PrePersist` for GST** — Rather than multiplying cost at each call site, the `Payment` entity applies GST exactly
once before every insert. This eliminates double-GST bugs and keeps pricing logic in one place.

**H2 locally, Supabase PostgreSQL in production — one dialect** — Local development uses embedded H2 in
`MODE=PostgreSQL` so there is nothing to install, while production uses Supabase PostgreSQL. The same `schema.sql`,
`data.sql`, and native queries run on both because they are written in portable, PostgreSQL-flavoured SQL that H2's
compatibility mode accepts verbatim (identity columns, `BOOLEAN`, `INTERVAL '30' DAY`, `ALTER … RESTART WITH`). This
keeps local iteration friction-free without introducing a dev/prod dialect gap.

**Revocable JWTs** — Every token carries the account's `token_version`. `JwtAuthenticationFilter` looks the account up
on each request (one indexed primary-key read) and rejects the token if the account was deleted or the version has moved
on — which happens on every password change and admin reset. `UserPrincipal` still carries `residentId` and `techId`
from
the token, so controllers don't need to load the account themselves.

**Guarded payment transitions** — Each payment query names the statuses it may move from (e.g. submit only from
`Pending`/`Overdue`, reject only from `Under Review`), so repeated or out-of-order calls change nothing and return
`400`.

**Manual IDs for amenities and technicians** — Both tables use non-auto-increment primary keys. IDs are admin-assigned,
which keeps the catalog stable and predictable (e.g., amenity 1 is always the Paddock Club Lounge). Adding a record with
an ID that already exists returns `409` and leaves the existing record untouched: the services insert with
`EntityManager.persist` rather than `save()`, which would merge into (overwrite) the existing row.

**Disposable seed locally, durable data in production** — Local H2 sets `spring.sql.init.mode: always`, so `schema.sql`
drops and recreates the tables and `data.sql` reseeds them on each start — a fresh, deterministic dataset every run.
Production sets the mode to `${DB_INIT_MODE:never}`, so **restarts never drop or reseed** and real data persists;
`ddl-auto: update` still reconciles the schema without dropping. A brand-new production database is seeded once by
deploying with `DB_INIT_MODE=always`, after which the flag is removed.

**`@Modifying(clearAutomatically = true)`** — The `updateTaskStatus` JPQL update clears the persistence context after
execution, preventing stale entity reads from JPA's first-level cache.
